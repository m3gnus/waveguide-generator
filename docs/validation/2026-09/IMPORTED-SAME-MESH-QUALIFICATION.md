The CAD returns are built by the harness, not exported from a CAD program:
`scripts/imported_ingest_fixtures.py` writes a STEP body with `hornlab-mesher`,
wraps it in a `.wgreturn` manifest the way the WGLink add-in writes a linked
return, and puts it through WG's own ingest. The "placed in CAD" and "edited in
CAD" rows are therefore not live-Fusion coverage.

The sphere frequencies (100 to 1,500 Hz on a 0.1 m sphere) stay below its first
interior Dirichlet resonance (ka = π, about 1,715 Hz), so no sphere row probes a
resonance.

Not covered here: imported BEMPP on an OpenCL device (see Environment); Windows
and Linux; the packaged application; returns exported by a live CAD session.

## Reproduce

On a macOS host with Metal and a provisioned BEAT CPU runtime, with an
interpreter whose HornLab modules match `pins.json`, from the repository root:

```bash
env -u JULIA_DEPOT_PATH \
  HORNLAB_BEAT_FORCE_CPU=1 \
  HORNLAB_BEAT_JULIA="<installed Julia 1.12.6>/bin/julia" \
  python scripts/qualify_imported_same_mesh.py \
    --json docs/validation/2026-09/imported-same-mesh-qualification.json \
    --markdown docs/validation/2026-09/IMPORTED-SAME-MESH-QUALIFICATION.md
```

The run needs both engines; with either missing it exits 2.
`scripts/tests/test_qualify_imported_same_mesh.py` checks the harness itself
without a solver, and `WG2_QUALIFY_IMPORTED=1` adds the real run to it.

The Scope and Reproduce sections, the Environment lines from
`hornlab-waveguide-mesher` down, the two paragraphs after the engine list, the
note on the least order, and the unjudged-row labels were added to the generated
record. No measured value was changed.

## Axial rows, per-source-axis-v2

Measured 2026-09-29 by `python scripts/qualify_imported_same_mesh.py --axial-only`
at `waveguide-generator` `75e49224` on Darwin arm64 (Python 3.13.1): Metal
(`hornlab-metal-bem` 0.2.0, `source_axes` build) and BEAT CPU (`hornlab-beat-bem`
`74da18c`, the pinned build, on its CPU path). **Provisional Metal figures:** the `source_axes` build's
`solve_multi_source` rejects a config whose axes cover more than one tag, so this run
used that build with its frame-resolution `replace` given `source_axes=None`; the
Metal rows are to be re-measured on the module's fixed build before this is final.
**BEMPP is not in these rows.** This
Mac has no OpenCL CPU device, the harness admits BEMPP only on OpenCL, and WG's
imported BEMPP path refuses numba, so the BEMPP axial rows are **owed on an OpenCL
host**; `hornlab-bempp-bem` covers its own `source_axes` contract in its tests.

The fixture is the equator-split sphere (tags `top` +z, `bottom` -z) with both
tags driven as separate axial channels, `front` and `back`. Their inferred axes
are +z and -z, recorded in each result's metadata with the contract version
`per-source-axis-v2` and asserted here. A unit acceleration of the whole sphere
along +z is `v_n = n.z`, which is `+psi` on the front and `-psi` on the back, so
the analytic oscillating sphere is `front - back`. The reference is the l = 1
outgoing wave `p = -rho cos(theta) h1(kr) / (k h1'(ka))` per unit acceleration
along the axis, in the time and drive convention of the breathing sphere
(`e^{-iwt}`, `dp/dr = -rho a_n` on the surface); its `k -> 0` limit is the
incompressible dipole. `front + back` is not that answer (the non-vacuity row).
The tilted copy turns the same mesh by 131 degrees about (1, -0.4, 0.7) with the
anchor frame left alone, so its axes are on none of X, Y, Z and the reference
dipole is turned with them.

observation point and frequency (the removed one-tag oscillating row read the same

negated copy and subtracted, which is why the `back` channel and `front - back`

refused by name on BEAT, at preflight and again when the solve is asked for:

which is not along the radiation axis. BEAT drives axial sources along its z axis
only. Solve it with Metal or BEMPP.*

# Windows measurements, 2026-09-30

Status: dated measurements on one Windows machine. They describe the commits and the
machine named here, not a release status.

This records what Waveguide Generator's CPU solvers do on a Windows PC without a GPU:
which OpenCL devices exist and compute, how fast BEMPP (numba and OpenCL) and BEAT CPU
solve the same meshes, how far their answers agree, what the application selects, and
whether the Windows installer builds, upgrades and uninstalls correctly.

## Summary

- **Fastest for a typical solve, once the application is running: BEMPP on the CPU
  OpenCL runtime.** A 20-frequency solve of the default OSSE takes 3.5–3.8 s on BEMPP
  OpenCL, 6.5–7.1 s on BEAT CPU and 15.7–16.0 s on BEMPP numba. OpenCL is about 1.9× faster
  than BEAT CPU and 4.4× faster than numba. The ratios hold on a full-3D mesh (9.2 s,
  19.4–20.3 s, 45–51 s).
- **Fastest for the first solve after a start: BEAT CPU.** 17.8 s against 26.5 s (OpenCL)
  and 84.1 s (numba) on the default OSSE. numba recompiles its kernels in every process;
  the first frequency alone costs 37–41 s.
- **numba and OpenCL give the same answer** (complex pressures agree to 4e-6). The choice
  between them is speed only.
- **BEAT CPU and BEMPP agree on resonance locations to 0.7 % up to 6 kHz** and on-axis
  level to 0.16–0.24 dB rms. Their largest disagreement on the default mesh, 14.8 % at
  7.4 kHz, is BEAT's order-2 quadrature being used up to k·h = 2.0; with order 4 the two
  engines agree to 2.8 % there.
- **The Intel CPU OpenCL runtime works on this AMD processor** and passes a real compute
  check. It is the only OpenCL device on the machine.
- **The Windows installer script did not compile** on `main` or on the installer branch.
  Fixed on three topic branches; with the fix every installer gate passes, including the
  upgrade-protection gates.
- **The OpenCL-first selection branch rejects a working device about one start in five**
  on this machine, because its device inventory is limited to 2.0 s.

## 2. OpenCL devices

One platform, one device:

| Platform | Device | Type | Driver | Vector width | Compute check |
|---|---|---|---|---|---|
| Intel(R) OpenCL (OpenCL 3.0 WINDOWS) | AMD Ryzen 7 5825U | CPU, 12 units, fp64 | 2025.20.10.0.23 (Intel CPU Runtime for OpenCL Applications 25.3.1) | 8 × float | **pass** |

The check runs a kernel with a known result (a multiply-add loop per work item) and
compares it with numpy, at two sizes eight times apart:

| Work items × iterations | Time | Maximum relative error |
|---|---|---|
| 262,144 × 256 | 2.6 ms | 5.6e-6 |
| 2,097,152 × 256 | 14.7 ms | 5.4e-6 |

Time grew 5.6× for 8× the work and the result is correct, so the device computes. The
same holds at the BEMPP level: per-frequency time grows with the mesh (0.13 s at 584
triangles, 0.42 s at 2,302, 2.27 s at 3,328 with quarter symmetry), and every OpenCL
result was checked against numba (section 4).

`hornlab-bempp-bem`'s own `check_opencl("cpu")` passes and costs 24.9 s cold in a fresh
process. Its `auto` selection only initializes the device; it does not run that check.
There is no GPU device, so `check_opencl("gpu")` reports none.

**The Intel runtime on an AMD processor.** Intel's page describes the runtime as
targeting Intel Xeon and Core processors. It works on this Zen 3 processor, with 8-wide
float vectors. Its licence (Intel End User License Agreement for Developer Tools,
August 2024 version, as installed) has no clause restricting it to Intel processors,
and permits redistribution only of files listed in a `redist.txt`. The installed runtime
ships no such list, so **bundling it is not permitted under the licence as installed**;
users have to install it themselves. Intel's page states that installing it requires
administrator rights. The newest release on that page is 2026.0; this machine has
2025.3.1.

PoCL is not installed. An earlier measurement on this machine found that PoCL on Windows
presents a device and returns all-zero matrices; it was not reproduced today.

## 3. Speed

All cases use WG's own mesher and solve path at `47893c0b`. numba was forced by pointing
`BEMPP_CPU_DRIVER` at a platform name that does not exist, which makes the pinned
`auto` selection fall back; every run's `assembly_backend` in the result metadata was
checked. BEAT CPU was selected with `--engine beat-cpu`. Each engine solved the mesh WG
built, with the same symmetry (`yz+xz` on the quarter cases).

### 4.1 Resonance locations

A 60-point sweep from 1 to 12 kHz on the default OSSE mesh, and the same sweep on a
refined mesh (3,328 triangles: 80 angular and 40 length segments, throat 3 mm, mouth
5 mm) as a reference. Peaks of the throat resistance, located by parabolic fit:

| Mesh, engine | Peaks up to 6 kHz (Hz) |
|---|---|
| Refined, BEMPP | 2074, 2728, 3445, 4204, 4983, 5802 |
| Refined, BEAT CPU | 2063, 2721, 3438, 4199, 4979, 5788 |
| Default, BEMPP | 2069, 2729, 3454, 4229, 5020, 5795 |
| Default, BEAT CPU | 2068, 2733, 3452, 4194, 4953, 5831 |

All four agree within 0.7 % up to 6 kHz. Above about 7 kHz the default mesh is
under-resolved for both engines (2.5 elements per wavelength at the mouth at 9 kHz): each
is 4–5 % median from the refined reference and the peak sets differ. On the refined mesh
the two engines still differ by 2.7 % median and 12.8 % at 12 kHz (1.0 dB on axis);
nothing measured here says which is closer to the truth.

### 4.2 Why BEAT and BEMPP part near 7 kHz on the default mesh

BEAT CPU's default regular quadrature is wavelength-driven: order 2 while
k·h ≤ 2.0 (h from the 90th-percentile element area), order 4 above. On the full-3D mesh
that is order 2 up to 7.4 kHz. Against the same solve at fixed order 4:

| Frequency (Hz) | k·h | Default order | Default vs fixed order 4 | Default vs BEMPP | Fixed order 4 vs BEMPP |
|---|---|---|---|---|---|
| 400–3,385 | 0.10–0.82 | 2 | 0.04–0.37 % | 0.2–2.4 % | 0.2–2.4 % |
| 4,110 | 0.99 | 2 | 1.3 % | 2.8 % | 2.0 % |
| 4,991 | 1.20 | 2 | 2.3 % | 3.2 % | 2.0 % |
| 6,061 | 1.46 | 2 | 6.1 % | 6.4 % | 2.7 % |
| 7,359 | 1.78 | 2 | 15.7 % | 14.8 % | 2.8 % |
| 8,936–16,000 | 2.16–3.86 | 4 | 0 | 2.2–8.5 % | 2.2–8.5 % |

(Patterns normalized on axis.) With order 4 throughout, BEAT CPU and BEMPP agree to
2.0 % median and 8.5 % worst over the whole sweep, and the 7.4 kHz outlier disappears.
Fixed order 4 costs 30.2 s per sweep against 17.5 s. The cutoff is read from the solve
request by the engine, but the Python `SolveConfig` could not set it; see section 5.

## 5. Can BEAT CPU get faster?

Measured through the `hornlab-beat-bem` API at the pinned commit on the full-3D mesh
(2,302 triangles, 1,153 degrees of freedom), 20 frequencies, a fresh worker per variant,
two warm sweeps each. "Cold" is worker start plus one sweep.

| Variant | Cold (s) | Warm sweep (s) | Against default | Error against default, median / worst |
|---|---|---|---|---|
| Default: 12 Julia threads, 4 BLAS threads, LU, fused assembly, single precision | 26.0 | 17.5 | 1.00× | reference |
| 1 Julia thread | 99.9 | 101.2 | 0.17× | 3e-7 / 5e-7 |
| 4 Julia threads | 36.8 | 30.0 | 0.58× | 0 / 0 |
| 6 Julia threads | 30.1 | 22.9 | 0.76× | 0 / 0 |
| 8 Julia threads | 26.1 | 19.5 | 0.90× | 0 / 0 |
| 1 BLAS thread | 22.0 | 16.8 | 1.04× | 3e-7 / 5e-7 |
| 12 BLAS threads | 23.7 | 18.3 | 0.96× | 2e-7 / 5e-7 |
| Forced LU | 21.4 | 16.9 | 1.03× | 0 / 0 |
| Forced GMRES | 22.4 | 16.5 | 1.02× | 9e-7 / 4e-6 |
| Double precision | 33.0 | 20.1 | 0.87× | 2.9e-6 / 2.4e-5 |
| Fixed quadrature order 2 | 19.5 | 13.8 | 1.27× | 0 / **3.3e-1** |
| Fixed quadrature order 4 | 36.0 | 30.2 | 0.58× | 1.9e-3 / 1.4e-1 |
| Fused assembly off | 34.0 | 25.8 | 0.68× | 3.9e-5 / 1.2e-4 |
| Precompiled engine bundle off | 45.2 | 17.3 | 1.01× | 0 / 0 |

Reading it:

- **Threads.** 12 Julia threads is the best setting and gives 5.8× over one thread. The
  package's default (`auto`) already uses 12.
- **BLAS vendor and threads.** They do not matter for these solves: the dense solve is
  0.7 s of 17.5 s. OpenBLAS was the only vendor measured; an MKL comparison could change
  at most that 4 %. The router chose LU; forced GMRES solved in half the time (0.35 s
  against 0.72 s per sweep), a 2 % difference overall.
- **Precision.** Single precision agrees with double to 2.9e-6 median and is 13 % faster.
- **Quadrature.** Order 2 everywhere is 27 % faster and wrong by up to 33 % above 8 kHz.
  There is no free speed there.
- **Cold start.** Julia starts in 0.33 s and the precompiled bundle loads in about 1 s.
  The remaining cold cost is compilation at the first solve: `--trace-compile` shows 104
  methods compiled at run time in a first solve through the worker, including
  `solve_request` and `main`. The bundle's precompile workload calls `solve_request` with
  a `Dict{String,Any}`, and the worker passes a `JSON.Object{String,Any}` from
  `JSON.parse`, so the cached native code is for a type the worker never uses. In an
  isolated probe the first call takes 0.21 s with the `Dict` and 1.43 s with the parsed
  object (50 and 72 run-time compilations). A one-shot solve through the worker takes
  5.8 s where start-up plus the solve account for about 2.5 s. Passing the workload's
  request through `JSON.parse(JSON.json(...))`, and giving it the options a WG request
  carries (symmetry, the sphere grid, surface traces), would move that compilation to
  build time. The bundle sources are verbatim copies of the upstream engine, so that
  change belongs upstream and was not made here. A PackageCompiler sysimage was not
  built: with the start at 1.4 s the first-solve compilation is the larger term, and a
  sysimage would need the same corrected workload to capture it.
- **AVX-512.** Not measurable on this processor.
- **MUMPS.** The pinned `hornlab-beat-bem` does not depend on MUMPS, has no
  `BLAB_MUMPS_SOLVE_THREADS`, and its exterior solve is dense. Independently of BEAT,
  `MUMPS_seq_jll` v500.900.100 (MUMPS 5.9.1) was installed into a scratch Julia 1.12.6
  project on this machine and driven through `zmumps_c` with a struct layout derived
  from its own header (10,920 bytes, 89 fields). **It loads and solves correctly on
  Windows x86-64, on one condition:** MUMPS calls BLAS through libblastrampoline's LP64
  interface, and Julia's default configuration forwards only ILP64 OpenBLAS, so
  `zgemm_`, `zgetrf_` and nine other symbols have no target until an LP64 BLAS
  (`OpenBLAS32_jll`) is forwarded. With that, on a complex-shifted 3D Laplacian:

  | Unknowns | Threads | MUMPS analysis / factor / solve (s) | UMFPACK factor / solve (s) | Relative error |
  |---|---|---|---|---|
  | 27,000 | 1 | 0.29 / 0.74 / 0.021 | 1.66 / 0.027 | 1.1e-15 |
  | 27,000 | 8 | 0.34 / 0.72 / 0.025 | 2.37 / 0.024 | 1.1e-15 |
  | 64,000 | 1 | 0.72 / 3.69 / 0.064 | 8.26 / 0.084 | 1.4e-15 |
  | 64,000 | 8 | 0.73 / 2.29 / 0.066 | 7.59 / 0.084 | 1.4e-15 |

  MUMPS factors 2.2–3.3× faster than Julia's built-in UMFPACK. The single-right-hand-side
  triangular solve is about the same. This matters for a coupled sparse solve, not for
  the exterior solves in this report.

**What it would take for BEAT CPU to match BEMPP OpenCL on this machine.** BEAT CPU
needs about 2× on a warm sweep, and assembly is where the time is. Its kernels are scalar
Julia; BEMPP's OpenCL kernels are compiled 8-wide. Thread scaling is already 5.8× of 12
virtual processors. So the remaining lever is vectorizing the assembly kernels, not a
setting. Against numba, BEAT CPU is already 2.3× faster warm and 3–5× faster cold.

**The quadrature cutoff, measured.** With the cutoff settable (the branch in section 9),
the same sweep against fixed order 4. These six runs shared the machine with another
job, so compare the rows with each other, not with the table above:

| Order-2 cutoff (k·h) | Warm sweep (s) | Frequencies at order 4 | Worst error against order 4 |
|---|---|---|---|
| 2.0 (default) | 19.9 | 4 of 20 | 13.4 % at 7.4 kHz |
| 1.5 | 21.9 | 5 of 20 | 5.9 % at 6.1 kHz |
| 1.25 | 22.5 | 6 of 20 | 2.2 % at 5.0 kHz |
| 1.0 | 24.0 | 7 of 20 | 0.94 % at 4.1 kHz |
| 0.75 | 24.1 | 9 of 20 | 0.29 % at 2.8 kHz |
| order 4 everywhere | 41.5 | 20 of 20 | reference |

A cutoff of 1.0 keeps the order-2 error under 1 % for 20 % more time on this sweep. The
branch changes no default.

## 6. What Waveguide Generator selects here

On `main` (`47893c0b`, and the installed build of `cbfdcd98`): `auto` resolves to
`bempp`, and BEMPP selects the OpenCL CPU device ("AMD Ryzen 7 5825U … (Intel(R)
OpenCL)") for free-standing, infinite-baffle and imported solves; `assembly_backend` in
the result metadata is `opencl` in all three. There is no GPU OpenCL device to select.
With OpenCL hidden, BEMPP falls back to numba and says so in the engine reason, the job
log and the result metadata. This agrees with section 2.

On `main`, selection initializes the device without computing on it; a device that
initializes and computes nothing would be selected, and WG's solve-path guard against an
all-zero result is what would catch it.

### 6.1 The OpenCL-first branch (`lander/ib-numba-route-qualification`, `f974f20b`)

The branch qualifies CPU OpenCL devices with a bounded assembly-and-solve check against
stored numba values, never selects a GPU device, and falls back to numba.

| Measurement | Result |
|---|---|
| Qualification, idle machine | passes in 3.5–5.6 s; matrix error 7.5e-7, solve error 9.9e-7 |
| Inventory probe alone | 1.60 s, against a limit of 2.0 s |
| Smoke probe alone | 1.9 s, against a limit of 5.0 s |
| Qualification with one numba solve running | 1 of 6 rejected: "OpenCL inventory timed out after 2.0s" |
| **Plain application start, idle machine (6 % load)** | **2 of 9 starts reported `assembly_backend: numba`, `opencl_unavailable_reason: smoke_test_timeout`** |
| Infinite-baffle solve, OpenCL route | 39.2 s cold, 4.6 s next |
| Infinite-baffle solve, numba route (pyopencl hidden) | 91.1 s cold, 16.8 s next |
| Accuracy, numba route vs OpenCL route | 3.8e-6 median, identical resonance locations |
| Capabilities with OpenCL present | `assembly_backend: opencl`, `hostPlatform: windows` |
| Capabilities with no OpenCL | `assembly_backend: numba`, `opencl_unavailable_reason: no_device` |

Three defects, reported to the branch's owner and not fixed here:

1. The 2.0 s inventory limit has 20 % headroom on an idle machine, and the probe competes
   with the application's own start-up.
2. The verdict is cached for the life of the process, so one timeout keeps the whole
   session on numba.
3. An inventory timeout is reported with the reason code `smoke_test_timeout`, so the
   user is told their runtime "timed out".

The installed-bundle run of `qualify_installed_cpu.py --ib-engine bempp` on this branch
was not done: the branch has no supported way to force numba in an installed bundle, and
the branch is being changed. A non-computing device (PoCL) could not be tested; it is
not installed.

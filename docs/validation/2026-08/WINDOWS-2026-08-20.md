### 3.4 Root cause — a Gmsh session corrupts the native Windows `PATH`

The first persistent break occurs after a request passes through
`run_on_gmsh_worker`. The endpoint itself can be reduced to one passing test
followed by one failing Git contract test:

```
test_endpoint_validates_workspace_and_returns_pipeline_record  PASSED
test_every_installer_file_exists_and_is_executable_where_that_matters  FAILED
```

This also reproduces without pytest. The minimum reproducer is:

```python
import gmsh
gmsh.initialize(interruptible=False)
gmsh.finalize()
```

After those calls:

- Python's cached `os.environ["PATH"]` still contains the original complete
  value, including `C:\Program Files\Git\cmd`.
- `GetEnvironmentVariableW("PATH", ...)` returns a different, truncated value
  ending in `...Intel\Shared Libraries\bin;C:\Program Files\Common
  Fil;C:\Users\Docker\AppData\Local\Programs\Python\Python313\`.
- `subprocess.run(["git", "--version"])` raises WinError 2.
- `where.exe git` finds nothing.
- `subprocess.run([r"C:\Program Files\Git\cmd\git.exe", "--version"])`
  still reports Git 2.53.0, proving Git itself and its DLLs remain loadable.
- `cmd.exe` also still starts by absolute path.

This is an empirically demonstrated Windows process-environment mutation in the
Gmsh 4.15.2 initialize/finalize path. Waveguide Generator does not currently
preserve and restore the native `PATH` around the session. Besides the suite
failure, it is relevant to the running application: any later feature that
spawns a program by name, including Git-backed update behavior, can fail after
the first Gmsh operation.

No fix was made. The work order requires stopping when an earlier gate failure
invalidates later phases; Phase 0 is also not one of the explicitly authorized
fix phases.

## 5. Changes and design assessment

No product code was changed. The only repository change is this dated evidence
report, committed on `feature/cad-link-ux` as requested. A temporary pytest
diagnostic plugin was created locally to identify the first broken subprocess
boundary and deleted before the branch switch.

No design fault was identified. The blocker is an implementation/runtime
integration defect: a native dependency mutates process-global Windows state,
and the long-running server does not restore it. Whether to fix that in the
Gmsh packaging layer or defensively around the application's Gmsh session was
not decided in this verify-and-stop run.

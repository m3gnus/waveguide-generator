## 3. Phase 0 — done after fixing Gmsh native `PATH` corruption

### Before the fix

The authoritative host-user run on released `main` finished **1511 passed, 23
skipped, 3 failed in 175.15 s**. The three late failures could no longer spawn
bare `git`; all three passed in a fresh pytest process.

The first persistent contaminator was later narrowed to
`test_occ_ingest_end_to_end_writes_tag_names_reuses_cache_and_solves`. Its
first direct `hornlab_mesher.cad.write_step()` self-owned a Gmsh session outside
WG's worker. Later direct CAD helpers and synchronous STEP/STL export seams did
the same.

Real Gmsh 4.15.2 changed the native value returned by
`GetEnvironmentVariableW("PATH")` from 1,555 characters to 316 while
`os.environ["PATH"]` retained the stale full string. Bare `git` then raised
WinError 2 although the absolute Git executable still worked. This reproduced
outside pytest with `gmsh.initialize()` / `gmsh.finalize()`.

### Fix and verification

The fix preserves the native Win32 `PATH` immediately around every owned Gmsh
initialize/finalize call and around synchronous export seams that can let the
pinned mesher own a session. POSIX remains a no-op. CAD tests now enter the
same `_run_in_gmsh_session` ownership path as production. The regression puts
a uniquely named executable only on native `PATH` and launches it inside and
after a real Gmsh session.

Main carries the local commits `e217823d` and `a5e0b8ed`; the equivalent
feature-branch commits are `bc6b644b` and `6fbaa66d`.

Post-fix evidence:

- server/scripts: **1515 passed, 23 skipped, 7 warnings in 163.77 s**;
- focused worker lifecycle/signal tests: **10 passed**;
- direct native probe: the 1,555-character `PATH` stayed byte-for-byte equal and
  bare `git --version` worked after Gmsh;
- frontend `npm ci` / `npm run build`: passed;
- `ruff check server scripts shared launch launchers`: passed.

This closed the blocker that invalidated the first attempt at this report.

## 6. Phase 3 — Windows Job Object fix and empirical containment

Phase 3 ran from `feature/step-parser-isolation`. The Gmsh fixes were applied
there as `18cdabfd` and `a7471ba9`. The isolation change is local commit
`bf9668ed` (`Fix Windows STEP child confinement ABI`).

### Before and after

Before the ABI fix, the Windows-only memory test **ran and passed** by itself
(1 passed in 0.53 s); it did not skip. The whole isolation module was **30
passed, 3 skipped, 1 failed in 11.03 s**. The failure was a POSIX-only `HOME`
assertion in the real-child environment test, not product leakage.

After the fix:

- isolation module: **35 passed, 3 skipped in 12.19 s**;
- full server/scripts branch: **1580 passed, 26 skipped, 7 warnings in 197.48 s**;
- frontend build: passed (1,326 modules, 4.83 s);
- required Ruff scope and `git diff --check`: passed.

### ABI finding

`CreateJobObjectW`, `SetInformationJobObject`,
`AssignProcessToJobObject`, `TerminateJobObject`, and `CloseHandle` now have
explicit `argtypes` and `restype`. `HANDLE` is pointer-sized; the process
handle and information buffer use `ctypes.c_void_p` where required.

A real post-fix probe returned:

```
CreateJobObjectW handle=232 (0xE8)
assignment=9.711 ms
blocked_before_envelope=True
```

The actual handle was small, so its upper 32 bits were zero. That explains why
the undeclared ABI happened to pass the pre-fix memory test on this machine;
no truncation failure was observed here. The fix still matters: ctypes's
default `c_int` contract was wrong and could truncate a future 64-bit handle.

### Five requested behaviors

| Behavior | Evidence | State |
|---|---|---|
| Memory containment | A real child committed memory past the 192 MiB process/job cap, was killed well before its 60 s deadline, surfaced as a stage-7 `ChildRefusal`, and a normal import immediately succeeded | **demonstrated** |
| Process-tree kill | A hanging child wrote its PID, spawned a real sleeping grandchild that wrote its PID, and both became non-live after the 3 s deadline; liveness used `OpenProcess` + `WaitForSingleObject`, not `os.kill(pid, 0)` | **demonstrated** |
| Parent exit | A separate parent was killed mid-run; closing its only job handle removed both recorded child and grandchild PIDs | **demonstrated** |
| Breakaway retry | Normal launches used the real breakaway path. The retry test injected only the first access-denied `Popen`; the retry child, no-breakaway flags, Job Object assignment, memory cap, and refusal were real | **partial** — the host allowed the breakaway flag even inside the dedicated nested job, so a natural retry trigger could not be forced |
| Environment allowlist | A real disposable child returned its own `os.environ`; inherited `ONSHAPE_*`, `WG_DATA_DIR`, database values, and real profile paths were absent; `USERPROFILE`, `APPDATA`, `LOCALAPPDATA`, temp, and cwd pointed under staging | **demonstrated** |

The only `WG_*` values deliberately present are the harness-created
`WG_ISOLATED_CAD_CHILD` marker and artifact-size limit; no inherited WG
authority crossed the boundary.

`child_main.py` remains stdlib-only at module scope. A real child stayed
blocked on stdin after assignment, and the 9.711 ms assignment left no
material startup window. No `CREATE_SUSPENDED` change was justified. The
fail-closed behavior and prohibition on an in-process fallback are unchanged.

The containment observations above came from real OS child processes, memory,
PIDs, and Job Objects through automated acceptance probes. They were not merely
mock-return unit tests; they also were not visually inspected in Task Manager.

Remaining unproven or unresolved:

- upgrade and rollback against a real populated v1 installation;
- `uninstall.bat --yes`, which is broken in released v0.2.4 as described above;
- a pristine sibling parity run because the sibling checkout contained user

- the three unrelated `feature/cad-link-ux` Windows portability-test failures;
- a naturally triggered breakaway retry in a parent job that rejects
  `CREATE_BREAKAWAY_FROM_JOB`;

No design fault was found. The isolation design remained fail-closed and never
fell back in-process. The defects were Windows implementation/integration
issues: native environment restoration, Win32 ABI declarations, a batch
argument shift, cross-platform test assumptions, and the skip helper doing
work after promising not to.
